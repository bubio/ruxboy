## 2. Rux 言語で分かったこと

`spikes/Sdl3Probe/NOTES.md`(実装着手前の実現可能性検証、2026-09-01)と、
その後の実装を通じて判明した言語仕様。

### エミュレーターコアと相性が良かった点

- **符号なし整数は debug/release ともラップする**(トラップしない)。GBC
  コアは `uint8`/`uint16` のラップアラウンドに全面依存するため必須の性質。
  実測で確認済み。**符号付き整数は debug でオーバーフローが致命的エラーに
  なる**ため、コアでは符号なし型を使う。
- **構造体は C とレイアウト互換**(宣言順・自然アライメント・並べ替えなし)。
  SDL3 の構造体を `extern` 宣言してそのまま渡せる。
- C の可変長引数関数(`snprintf` など)を呼べる。Rux 独自の可変長引数
  (`T...`)とは別物。
- コンパイル時分岐 `when #target.os == .macOS { ... }` が使え、取られな
  かった枝は解析されない(他プラットフォーム専用シンボルを書ける)。
- 固定幅整数(`uint8`〜`uint512`)、`*T`/`*var T` の読み取り専用/書き込み可
  区別、`*opaque`(`void*`)が揃っている。

### 制約になった点

- **モジュールスコープに可変変数を置けない**(`const` のみ)。状態はすべて
  構造体に入れてポインタで持ち回る設計になる(`Cpu`/`Bus`各構造体)。
- **配列は `.data` を持たない**。`Slice<T>` だけが持つ。先頭アドレスは
  `@array[0]`。
- 多次元配列の前例が無く、VRAM/WRAMバンクなどは1次元配列にフラット化して
  対応した(フェーズ6コミット参照)。
- `variant`(タグ付きユニオン)は**タグが非公開でシリアライズ不可**。
  セーブステート(フェーズ7)を見据え、`Mbc` はタグ付きunionではなく
  **フラット構造体**で表現する設計判断をフェーズ4の時点で行った(結果、
  フェーズ7で「MBC種別ごとのサイズ分岐が不要」という利点として効いた)。
- 浮動小数点(`float32`)は Rux 側での使用実績が薄く構文リスクを避けるため、
  APU(フェーズ5)は**整数演算のみ**(量子化された生の単位 -15..15 のまま
  ミキシング)で実装した。
- **整数値に対する `match`(switch相当)が存在しない**。`match` は
  enum/variant 専用(`Docs/Language.md`、標準ライブラリの使用例もすべて
  enum/variant)。
- **関数ポインタ・第一級関数値が(ドキュメント上)存在しない**。
- パッケージ間の依存は**レジストリ未公開**のため `external/Rux/Packages/`
  への相対パス依存で解決する(絶対パス・symlink不可、推移的依存も自分の
  マニフェストに列挙、詳細は `spikes/Sdl3Probe/NOTES.md`)。
- `rux fmt` は `Rux.toml` のコメントを消す。

### Rux コンパイラのバックエンド上の制約(パフォーマンスに直結)

`external/Rux/Docs/Architecture.md` に明記の通り、Release パイプラインは
**定数畳み込み・コピー伝播・DCE・CFG整理のみ**で、以下を一切持たない:

- `mem2reg` 相当(スタック/構造体メモリ上の変数をレジスタへ昇格する処理)
- LICM(ループ不変式の巻き上げ)
- 関数インライン化
- switch/if-else チェーンのジャンプテーブル化

これにより「同じフィールドに複数回触れる」「小さなヘルパー関数を何度も
呼ぶ」という、他の言語(C/C++ -O2、Rust release)なら気にしなくてよい
書き方が、そのまま「毎回メモリを読み直す」「毎回呼び出しオーバーヘッドが
乗る」機械語に直訳される。詳細と実測データは3章・`docs/PerformanceNotes.md`
を参照。

### Rux ツールチェインの運用上の制約

- **`--emit asm`(実名付きアセンブリ出力)は x86-64 ターゲット限定**。
  AArch64(実行・プロファイル対象)では無効。
- **AArch64 バイナリは Debug/Release ともローカルシンボルを一切保持しない**
  (`nm`で定義済み関数が1つも出ない、DWARFなし、dSYMも生成されない)。
  `rux build --help` は `--debug` を「Build with debug symbols」と説明する
  が、実態は伴っていない。Instruments で直接シンボリケートすることは
  現状できない。
- `--define` は `build`/`run` にはあるが `lint` にはない。
- 標準ライブラリはレジストリ未公開のため `rux add` は使えない
  (2章参照)。

上流の Rux コンパイラ自体の既知の不具合一覧は
`external/Rux/Docs/CompilerDefects.md` にある(RuxBoy が直接踏んだものは
今のところ無い)。

## 3. パフォーマンス調査で分かったこと

詳細・実測データは `docs/PerformanceNotes.md` に分離して記録。要点のみ:

- CpuPerfベンチ(`Tests/Packages/Core/CpuPerf`、`NOP; JP 0x0100` ループで
  200M T-cycle 消化)を指標に、Release で `t-cycles_per_sec`/実時間比を
  継続計測してきた。フェーズ1.5時点(CPU+Busのみ、PPU/APU/Timer未実装)
  では 86.47M t-cycles/s(2061%)だったが、各サブシステムが実装されて
  `BusTick` から毎回呼ばれるようになるにつれて低下した(機能追加に伴う
  自然な低下であり、性能の後退ではない)。
- CpuPerfでサブシステムを個別に無効化する差分計測により、ボトルネックが
  PPU(約51%)・APU(約24%)・Timer(約16%)であると特定(`3f6f4b8`)。
  原因は Rux 言語自体の遅さではなく、上記「関数インライン化を行わない」
  という Release パイプラインの制約。
- 対策はすべて**「コンパイラが本来自動でやるべき最適化を手で肩代わりする」**
  という同一方針:
  - `TimerTick`/`ApuTick`/`PpuTick`: ホットループの内側で毎回呼ばれる
    小さなヘルパー関数を手動インライン化
  - `TileMapPixel`/`PpuRenderSprites`: 同一タイル内の隣接ピクセルで
    VRAM読み出しが重複していたのを、タイル境界が変わったときだけ
    再フェッチする1ピクセルフェッチャー相当のキャッシュに書き換え
  - `PpuTick`: `dot`/`ly`/`mode`/`windowLine` をループ外でローカル変数化
    し、呼び出しをまたぐ箇所だけ `bus.ppu` と同期(`mem2reg`の手動代替)
  - `CpuExecute`: 実ゲームで最頻出の命令群(LD r,r'・ALU A,r・INC/DEC r・
    JR)を分岐チェーンの先頭へ並べ替え
- 各対策後、`scripts/test.sh --release` 全PASS(既知のexpected-fail込み)、
  dmg-acid2/cgb-acid2 のフレームバッファハッシュ完全一致を都度確認して
  リグレッションが無いことを担保している。
- **`CpuExecute` を「最大のホットスポット」と最初に報告したのは誤りだった**
  (関数サイズからの推測に過ぎず、実測では分岐位置の効果は+5.5%程度に
  留まり、コスト自体は特定の1関数でなく呼び出し連鎖全体に広く薄く
  分散していた)。詳細は `docs/PerformanceNotes.md` 参照。
- **結論として、現時点ではこれ以上のソースコード側の性能対策は行わない
  方針とした**(根本原因は Rux コンパイラの未成熟さであり、コンパイラの
  改善を待つのが筋が良いと判断)。

## 4. エミュレーション精度の落とし穴集

移植・実装時に踏んだ、Game Boy / Game Boy Color 実機の非直感的な挙動。
ソース中に `落とし穴` というコメントキーワードで統一して残してある
(`grep -rn 落とし穴 Packages/Core/Src/`)。

### CPU / 割り込み

- **EI の効果は次の1命令実行後まで遅延する**。割り込み受理チェック(命令
  直前)より後・命令フェッチより前で解決しないと、EIが連続すると IME 有効化が
  いつまでも先延ばしされるバグになる(`7df20db`で修正、delay値も2→1に
  修正)。

### PPU

- **LCD off中はLYC比較器が停止する**(Mooneye `stat_lyc_onoff`)。STAT bit2
  (LYC==LY)は直前の値を保持し続け、off中のLYC書き込みも比較結果に反映
  されない。再計算が起きるのは PPU再有効化(比較器の再起動)のときだけ。
- **CGBモードでは LCDC bit0 の意味が変わる**(T6-5)。DMGでは
  「BG/ウィンドウ全体の有効/無効」だが、CGBでは「BG/ウィンドウの
  マスタープライオリティ」になり、0でもBG/ウィンドウは通常どおり描画
  され続け、OBJが常にBGより前面になるだけ。白一色化はDMGモード限定。
- **CGBのBGタイル属性バイトは「バンク1のタイルマップと同アドレス」から
  読む**(Pan Docsに明記された仕様上の落とし穴)。
- **CGBはOBJの優先度がX座標に関係なくOAM順**(先頭が勝つ)。DMGはX座標が
  小さいスプライトが勝ち、同Xなら OAM 順、という違いがある。
- OAM DMA中: bit7は「非アクティブ」を表すので進行中は0のまま、下位7bitに
  残りブロック-1を返す(FF55読み出し)。

### HDMA / CGBレジスタ (Bus.rux)

- BCPS/OCPS(パレットインデックス)は**書き込み時のみオートインクリメント**
  (読み出しでは増えない)。
- HDMA関連レジスタは軒並みビット単位の落とし穴がある: FF52(下位4bit無視)、
  FF53(上位3bitマスクで常に0x8000起点)、FF54(下位4bit無視)。
- **DMGモードではVBK(FF4F)/SVBK(FF70)書き込みは無視**され、バンク0固定の
  ままにする。

### ダブルスピード (CGB, T6-6)

- ダブルスピード中、**CPU/Timer/シリアルは2倍速、PPU/APUは等速**で進む
  (「CPUの1 M-cycleにつき、PPU/APUへは2 T-cycleだけ供給」する方式)。
  **これを逆にすると Timer の音程が半オクターブずれたり、ゲームが倍速に
  なったりする**。Timer/OAM DMAはCPU側の生T-cycle(`tCycles`)のまま進め、
  PPU/APUだけ `hwCycles`(倍速中は半分)を渡す、という非対称な配線が必要。
- フェーズ8実装中に見つけた実バグ: フレーム境界判定に `bus.cycles`(CPU
  生T-cycle、倍速中も半分にならない)を使っていたため、ダブルスピード中の
  映像更新とオーディオ生成量が本来の半分になっていた。実ハードウェア時間
  で正しく進む `bus.hwCycles` を使うよう修正済み(`678944e`)。

### カートリッジ / MBC

- **MBC2 はヘッダの0x0149(RAMサイズコード)に関わらず、常に内蔵
  512x4bit RAM を持つ**。上位4bitは読むと1固定(0xF0マスク)、実データは
  下位4bitのみ。A000-A1FFが本体で、A200-BFFFはエコー(0x200バイト境界で
  繰り返す)。
- **MBC2 のRAM有効化とROMバンク切替は、MBC1と違い同じアドレス範囲
  (0000-3FFF)内で bit8 により区別する**(MBC1は別々のアドレス範囲で
  区別する)。
- **MBC3のRTCラッチは「0x00を書いてから0x01」の遷移のみ**ラッチが発生する。
  それ以外の値を書くと `latchPrepared` フラグがfalseにリセットされる。
- **MBC5はMBC1/MBC2/MBC3と違い「バンク0は1に読み替える」癖を持たない**。
  バンク0をそのまま4000-7FFFに指定できる。

### APU

- スイープユニット: **negate計算後に正方向へ切り替えるとチャンネルが停止
  する**(dmg_sound "04-sweep"系テストで判明)。`negateCalculatedSinceTrigger`
  フラグで追跡している。

### セーブステート

- **リングバッファ(APUのサンプル出力用)は保存対象に含めない**(単なる
  出力先バッファであり、ゲーム状態ではないため)。復元直後は空という
  前提を実際に成立させるため、`ReadApuState` はインデックス
  (ringRead/ringWrite/ringCount)を明示的にクリアする。これを怠ると
  復元前の古いサンプルが復元後も再生され続けるギャップが生じる
  (BubiBoyLite T20-6相当の対策)。
- 検証方法として、「復元後に実行を再開したら元のまま続けた場合と同じ
  状態に収束するか」を新規インスタンスで比較する分岐テストを採用
  (フィールド保存漏れを検出しやすい)。

## 5. 既知の未解決差分(expected-fail)

`scripts/test.sh` は以下を**既知の差分として許容**しており、PASSしなくても
リグレッションではない:

- **Mooneye `rapid_toggle`**: 既知のタイマータイミング差。
- **Mooneye `reti_timing`**: OAM DMA実装後、タイムアウトではなくROM自身の
  アサーション失敗まで進むようになった(DMA自体は機能している)。RETI直後の
  DMA起動タイミングに関する孤立した時機差が残る。
- **Mooneye `stat_lyc_onoff`**: LCD off中のLYC比較器停止(4章参照)を実装
  した上で、ROM内4ラウンドのうち検証しきれていない分岐が残る。BubiBoy Lite
  側もこのROMをテスト対象にしていない。

## 6. 開発プロセス上の決め事

- **コミット・プッシュは毎回その場の明示的な指示があるまで行わない**
  (`docs/dev`・本体リポジトリいずれのリモートもプライベートで、push は
  GitHub Actions CI の使用量を消費するため。`1c59477` で「一連の作業内でも
  都度確認が必要」と明文化)。
- `docs/dev/`(フェーズ計画)は private submodule。フェーズごとの実装完了時に
  「chore: update dev docs submodule」コミットで同期する運用。
- ソースコードのコメントは `///` doc-comment 形式に統一し、`rux doc` で
  ドキュメント生成可能にしてある(`2960a94`)。
- CI は `docs/**`・`spikes/**`・`**/*.md`・`.gitignore` のみの変更では
  スキップする(`c1c8c87`)。
- `docs/BluePrint.md` は要求仕様の唯一の源で**編集禁止**(入力文書のため)。
  逸脱はユーザー承認を得て記録する(このファイルはその記録の一部)。
